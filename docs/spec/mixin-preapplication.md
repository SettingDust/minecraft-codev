# Mixin Pre-application

**Status: Target-aligned technical contract — the three-diagram design, duplicate-object-key policy, unescaped-string-control-character policy, subsequent eight-point simplification, default UTF-8 decoding and JDK resource-open failure semantics are accepted; new-design implementation, verification and acceptance are not established.** Technical owner: `minecraft-codev-mixins`, with the user deciding downstream output use and integration. These are system boundaries, not newly appointed maintainers. **Must**, **must not**, and **may** express requirements and permitted behavior for the target below; they do not describe verified implementation.

## Authority and boundary

The authorized target is for Codev to implement and execute real Mixin pre-application and exact configuration-entry cleanup, using logs and exceptions for diagnostics. In a complete cleanup flow registered and composed by the caller, the consumed target must contain the real engine's processing output and the processed configuration copies must no longer contain entries whose logical identity received an engine application notification. Codev does not additionally prove error-free or complete application. Returning a removable-entry list alone does not complete that cleanup; the user must not have to implement the strip algorithm or JSON edits, but must register, configure and consume Codev's Strip Transform as specified below. The user has also explicitly settled that Codev does not restrict output consumers or purposes; downstream use and integration are the user's decision. This updates the existing owning Spec, not a second Spec. The earlier scope maintenance did not authorize planning or implementation; the user has since separately authorized documentation alignment and planning preparation, not production implementation.

## Supplied materials and resolution

The following are logical input/output roles. The selected names and file representation are specified below; this table does not freeze other public signatures or introduce a new versioned schema:

| Role | Required behavior |
| --- | --- |
| Target | A readable target JAR whose class bytes are in the declared target naming namespace. The output is a separate build copy, never an in-place update. |
| Mixin sources | The artifacts carrying the specified configurations, Mixin classes, refmaps and associated resources. Configuration discovery is limited to these sources and the target; merely appearing on the resolution classpath does not register every configuration there. |
| Resolution inputs | Ordered dependencies, including executable task plugins and their resources. Ordinary classes, plugin dependencies, class bytes and resources use one task domain with precedence **resolution classpath → Mixin sources → target**, preserving order within each collection, as retained by the ADR. |
| Environment | Effective side (including an explicitly represented unknown side when applicable) and implementation dependencies. General engine options must use Mixin's native reads of host system properties and default behavior; Codev must not reinterpret those rules or expose a Task-level public `engineOptions` or equivalent general raw-override entry point. Side and naming inputs retain their dedicated parameters. These determine the actual operation, not an assumed Loader environment. |
| Naming inputs | Optional mapping file and explicit source/target namespaces, plus the refmap context when needed. Compatible names require no mapping. |
| Destination and consumers | Separate destinations for the transformed target and processed dependency copies, distinct from every protected input. Output availability depends on the requested component's completed production and publication or valid current-input build reuse, regardless of downstream purpose. A normally completed Task target may be consumed as applied, not automatically as stripped; a complete cleanup flow requires consumption of all corresponding completed Transform results. An independently supplied old JAR path is not evidence of current completion. |

Outside the engine-native handling described here, unusable required engine inputs, malformed applicable engine configurations and ambiguous required engine input resolution must fail clearly rather than guess the execution inputs. Strip's separate trusted-input boundary below does not require an additional validity-proof pass. Actual configuration, parent, class, plugin and refmap reads use the supplied inputs and defined loading precedence; they need not originate in one physical JAR. Side/plugin selection, required/optional handling and plugin/refmap availability or fallback belong to the engine. A missing plugin/refmap that the engine handles normally, including by logging or returning a default mapper, must not be upgraded to a Codev failure. Necessary mapping inputs and explicitly requested refmap contexts remain required. Repeated configuration resource paths or cleanup identities across JARs are not, by themselves, invalid inputs and must not trigger a per-source uniqueness check. Cleanup matching uses the logical identity below, without a source identifier or origin-record artifact; it does not replace the remaining business-input and I/O responsibilities.

Platform classes and the Codev/Mixin/ASM implementation set retain their defined loading domains. Host-only application classes must not override task classes while resources come from task inputs. Task dependencies must not replace an arbitrary subset of the execution set or select a competing Fabric/Forge Mixin service/global-property implementation. Resource lookup must be accounted for by inputs: an intentional external-file facility needs tracked contents; implicit current-directory or host-classpath fallback is not permitted. Archive class names use ZIP `/` segments on every host, including Windows.

JDK `getResourceAsStream` semantics apply at the loader resource-open boundary: an `IOException` while opening a resource may yield `null`, treated as resource unavailable, without preserving the original cause. Codev must not add an open wrapper or pre-read solely to restore that cause. A required input that is consequently unavailable must still fail clearly; native plugin/refmap unavailability may follow the engine's normal fallback. This exception covers opening only: actual read/close failures after a stream is obtained, direct file/JAR I/O, output writes and selector restoration retain their failure obligations. Native exceptions caught internally with normal fallback remain subject to the engine policy; this does not authorize Codev to catch and ignore failures or guarantee propagation of every internally caught engine exception.

## Mixin configuration discovery and handlers

Host-side Loader discovery uses `MixinListingRule : FileListingRules` with covariant `load(root: Path): MixinConfigHandler?`, and `MixinConfigHandler : ListedFileHandler`. Core signatures are reused, not expanded into a Mixin or Jar-in-Jar framework. Core `list`/`remove` describe listing references and editing reference declarations, not only included JARs or mandatory deletion of physical files. The Mixin handler retains a `references: List<MixinConfigReference>` snapshot carrying `resource: String` and `side: ConfigSide`; `list(root)` exposes the referenced resources. Resource/side association and explicit metadata editing remain Mixin responsibilities, without a separate `environments` capability interface.

`MixinConfigHandler` must retain real, explicit current-metadata editing through `remove(root: Path)` and must not expose a public `removeConfigs` entry point. Removing that public entry point has source/binary compatibility consequences; out-of-repository callers are unknown, so absence of compatibility impact must not be claimed. This is the target interface requirement, not a claim that code removal is complete. Fabric owns its JSON adapter. `ForgeMixinConfigHandler` handles only Manifest `MixinConfigs` comma-separated references; `NeoForgeMixinConfigHandler` handles only `META-INF/neoforge.mods.toml` `mixins` tables and their `config` values. Discovery must visit all applicable listing rules: when both formats exist, neither is a fallback hidden by the other. No combined handler or cross-format set-equality condition is required. TOML extension fields such as `environment` must not be reinterpreted as Fabric side.

Each adapter parses/validates its business fields at actual load/edit boundaries and edits the current metadata, preserving unrelated attributes, fields, tables and unknown content. A loaded reference snapshot must not overwrite later additions; snapshot age alone must not reject an edit. Parsing and editing stay at these boundaries, without a separate duplicate pre-read/reference-validation pass. TOML load, save and close belong to its adapter and their real failures propagate. This does not authorize automatic metadata edits during pre-application. `StripMixins` must neither discover Loader metadata nor call these editing methods; its exact configuration-array editing is independent of the handlers. The design does not freeze every enum value, additional signature/ABI or a new null/empty-handler policy, and does not redesign Core or Jar-in-Jar.

## Naming and environment semantics

No mapping tuple means ordinary engine name resolution with effective default/explicit settings, not an unconditional new `REFMAP_REMAP=true`. Supplying any mapping component requires a readable, valid mapping file and nonempty source and target namespaces present in its header; validation must precede output writes. The source namespace describes selectors **after refmap resolution**; the target namespace describes the input target bytecode. Direction must not be guessed from filenames or Loader names, and `official` must not be aliased to `named` by assumption.

Refmap context is a separate effective input. An explicitly requested context must exist and remain fixed for actual member and class remapping, including against conflicting host defaults; otherwise the engine's usable, unambiguous defined default may be used. Multiple contexts without such a default require an explicit selection. A context alone does not enable mapping mode. No-refmap/default-mapper inputs must not be rejected merely for lacking a refmap, including in mapping mode when the normal selector chain suffices.

Use the ADR's locked-engine **`refmap(reference) → MemberInfo → environment remapper chain`** with a mapping-io adapter, not ad hoc refmap JSON string replacement. Mapping-io `0.7.1` is the retained repository precedent, not a promise of every mapping format or inherited-member inference. The local adapter is named `TinyMappingRemapper` rather than `ExactMappingRemapper`; this is a rename, not a Tiny-only input restriction. Existing `MappingReader` format handling and the owner/name/descriptor, directional, null/unmapped and ambiguity semantics below remain unchanged. The contract does not require the entire Codev remapper service or a new remapper architecture.

Member lookup must use source `(owner, name, descriptor)` and obtain the target name from the same mapping entry. Classes, field descriptors, method parameters/return types and array element types map source → target; reverse/unmap uses target → source. Missing mappings or null target names leave the affected component unchanged; null member names remain null. An incomplete owner/descriptor permits renaming only when available identity proves uniqueness. Otherwise leave the selector unchanged with an ambiguity diagnostic and let the engine perform normal matching and required-failure handling. A first same-name match or another owner's inferred inherited mapping is forbidden. Unsupported custom refmap forms must not be silently rewritten or advertised as supported.

For example, `a/A.run(I)V`, `a/A.run(Ljava/lang/String;)V` and `a/B.run(I)V` remain distinct lookups; an ownerless, descriptorless `run` cannot borrow the first one's mapping. `([La/A;)La/B;` maps each class component in the declared direction. Syntactically valid but semantically wrong namespace declarations cannot be inferred correct by Codev; required resolution failures remain visible engine failures.

## Operation ownership and resources

Each operation must create a **fresh operation runtime classloader** and own its bootstrap, Codev service/global-property state, environment, transformer, configuration registration, metadata caches, remappers, result/diagnostic state, extension instances and task-plugin static state. Applying the Gradle plugin must not initialize a shared transformation environment. A successful, failed or cancelled operation must not alter a later operation through retained Codev-owned state.

The host `Mixin` Task must own Gradle parameters, input/output and cache tracking, and Fabric/Forge/NeoForge configuration-reference discovery. Each invocation must create an `IsolatingMixinClassLoader` and use it to load a real Kotlin child function that processes the whole target JAR. The child must parse configurations and mappings, initialize the engine, process the archive into a staged target and collect notifications. After closing its archives, it must return fully materialized JDK Map/Set values carrying configuration resource paths and original entry strings. The host must close the loader before writing the completed entry file and completing the two named outputs. Neither Kotlin/serialization DOM objects nor live engine objects may cross that boundary. No fixed full function signature is prescribed.

The realization is Kotlin-first and uses the existing Kotlin serialization DOM, not a translation of the old Java class diagram into a same-shaped framework. Ordinary Kotlin/NIO, existing JAR and loader resource APIs with scoped `use` handle resource access and closure; serialization stays with host output writing and Strip input/editing. No separate `ArchiveResources` layer, `AppliedMixins` codec utility or same-shaped replacement layer is needed. It requires no `EngineOperation` control layer, `StrictJson` wrapper or replacement syntax scanner, custom engine-JAR SHA allowlist, or generic `OperationPublication` framework. Removing those framework prerequisites must not remove real isolation, Codev SPI/service ownership, coherent class/resource resolution, original exception causes except for the JDK resource-open boundary above, TCCL restoration, resource closure or tracking of actual execution dependencies, including Kotlin/serialization dependencies that affect output.

Codev execution implementation, `net.fabricmc:sponge-mixin:0.15.0+mixin.0.8.7` and its selected ASM dependencies form one coherent implementation set. Cross-loader values must use JDK types/simple values; incompatible Mixin/ASM instances must not be cast between domains. Output-affecting inherited native options and their relevant unset/default states remain identifiable and trackable build inputs. Internal host-property observation serves Gradle input tracking, not a hidden per-Task override API; Codev must not recompute Mixin option inheritance/parsing, inject an independent option snapshot or adapt option-getter bytecode. No operation-local `System` property table or independent raw values per Task in a shared JVM are promised.

Service selection uses the native `mixin.service` (`IMixinService`) and `mixin.bootstrapService` (`IMixinServiceBootstrap`) selectors during a short initialization window instead of loader-synthesized service-resource redirection. Before any child engine initialization, participating Codev operations/host copies must share one JVM-wide initialization exclusion boundary, save both selectors' original values or unset states, temporarily select Codev's child-domain service/bootstrap, initialize and cache the child service, and install/cache an operation-owned child global-property service. `IGlobalPropertyService` has no native selector property; setting the two selectors alone is insufficient. The global-property installation remains a locked-engine adaptation point, not a new public selector or specified private-field contract.

The selectors must be restored in `finally`, including on initialization failure or cancellation; an originally unset selector must become unset again. Restoration failures must propagate while preserving any earlier cause, never report success. Release the initialization exclusion only after restoration; it must not serialize the whole transformation. Cached child service/global-property state remains operation-owned so transformations can proceed independently and concurrently. Other, nonparticipating hosts may observe or interfere with these temporary JVM-global values; the window does not provide an unobservable sandbox. No property-lease or general locking framework is selected. Changed TCCL must also be restored in `finally`; owned classloaders, streams and ZIP filesystems must close after success, failure or cancellation.

Codev must not perform explicit `Thread.currentThread().isInterrupted` polling. Setting a thread's interrupt flag alone is not guaranteed to be detected or to prevent completion/publication when the invoked APIs do not throw. Cancellation or failures actually reported by I/O, engine, close, move or cancellation APIs must still propagate outward and trigger the required restoration, closure and failure cleanup; genuine cancellation must not become success.

Independent concurrent operations must have independent mutable state and temporary locations and agree semantically with serial processing. Processing targets sequentially within an operation is permitted; no parallel-speedup guarantee is implied. Conflicting output destinations must be rejected or exclusively owned through completion, never interleave results. This includes the Task's two outputs being physically distinct from one another. A shared-output conflict means producers writing the same physical destination, not multiple consumers reading a completed output. No general locking framework across arbitrary directories of independent builds is required.

Task plugins may initialize extensions in the scoped environment. Classloader isolation is **not an arbitrary-code sandbox** for plugin-written global properties, external threads, native state, filesystem or network side effects. Such effects must not be claimed contained without evidence. The current target requires no automatic engine upgrade, MixinExtras bundling/bootstrap or Loader-version predicate inference. Actual incompatible bytecode/configuration, missing injectors and bootstrap failures retain engine failure semantics; no broader Minecraft × Loader × extension support matrix is certified.

## Real results and diagnostic honesty

Codev must invoke the real Mixin engine on the supplied target and collect the application notifications it provides. The child performs only the original-entry reads needed for notification keys (including parent traversal as needed), side/mapping setup, configuration registration and real per-entry transformation; target-JAR `@Mixin` definitions must be preserved. It must not duplicate DOM reads for pre-validation, scan every declared class/plugin/refmap for existence or same-JAR origin (including inactive or plugin-excluded entries), independently prove parent validity, or inspect all configurations after transformation to revalidate active/environment/plugin/refmap consistency. Ordinary visited tracking for entry-reading traversal is not a second parent validator. These checks must not be moved into another helper under a different name. Actual reads, the default UTF-8 decoding policy below, business shapes and paths, required mapping/context selection, cancellation reported by actual APIs and genuine engine/I/O/close exceptions remain responsibilities. An engine application notification qualifies the corresponding logical cleanup identity immediately; configuration discovery or prepared/candidate lists alone do not. A notification does not certify complete application across targets or physical sources, error-free processing or final bytecode effects. Codev must not independently validate injection semantics, reconstruct or compare native target obligations or option rules, compare bytecode effects or parse logs as a cleanup-eligibility gate. A normal engine return is neither required as separate proof of an identity's eligibility nor proof that every requested application succeeded; Codev's own output-production obligations still apply.

Notification recording must use the accepted `GradleMixinRecorderExtension` contact point, which can obtain both the config and its corresponding Mixin, and map them back to the full configuration resource path and original explicit entry string. It must not rely only on audit class names to guess configuration ownership or introduce a new notification-attribution proof gate. This contact point does not certify every candidate, all-target completion or final effects; discovery alone remains insufficient.

Normal application/build logging must make the engine's processing and diagnostics available for the user to read. Codev must not interpret those logs to classify application success. Codev's own failures must be visible through logs or outward exceptions identifying the stage, relevant configuration or target when known, and the underlying cause when available; reflective wrappers must retain available causes. The JDK resource-open boundary above does not guarantee a cause for an unavailable resource. Unknown attribution or effects must remain explicit uncertainty, never an invented identity or a claim of complete application. Diagnostics use logs and exceptions, not a required return payload or persisted diagnostic ledger. No logging carrier, fields, format, return-log callback, separate records file, manifest, receipt, hash protocol or consumer replay is selected.

Exceptions thrown by the engine must propagate outward and stop the affected production; Codev must not swallow them or change injector requirements to manufacture success. When the engine logs errors or only partially applies Mixins but returns normally, this alone **must not fail Codev's output production or disqualify notified cleanup identities**. This includes native side/plugin decisions, required/optional behavior and unavailable-plugin/refmap fallback, including a normal default-mapper return; Codev must not reclassify these outcomes through pre-scans or post-processing checks. Required mapping and explicit refmap-context semantics remain in force; an unknown custom `refmapWrapper` must not be rejected merely because the field exists, silently rewritten or advertised as compatible. Such processing may leave mutations; partial application is not proof of rollback, and completed output must not be labeled “all requested Mixins succeeded.” The old selective residual-mutation/runtime-retention rejection is not a fatal rule for this target. Failure or unknown completion of Codev's own output production remains a failure, distinct from unknown application completeness or effects.

A valid operation with no applicable configurations may complete an unchanged build copy. With no application notifications, the removal set is empty and no configuration entries are removed; this does not assert that no engine processing occurred. Codev must not fabricate notified identities or reuse a prior operation's effects. An empty removal set establishes neither output completion nor application success, and invalid inputs outside the engine-native policy are not an empty-success shortcut.

## Applied outputs and exact dependency cleanup

For a complete cleanup flow registered, composed and consumed by the caller, Codev must produce the completed transformed target and processed dependency copies whose configurations no longer contain any physical occurrence matching a qualified cleanup identity, including cleanup of the derived target when it contains configurations. The caller must consume all required Transform results; a normally completed Task target alone is an applied target, not proof of cleanup completion. These are actual result requirements, not a requirement for an aggregate provider or unified Codev delivery exits. The logical identity is exactly the pair **configuration resource path + original Mixin-array entry string**. The resource path is the configuration's archive resource path, not the filesystem path of its source JAR. The entry string is the JSON string value as written in the configuration's `mixins`, `client` or `server` array, before package expansion or name mapping; an expanded or mapped class name must not replace it. Array section, index and physical source are not identity components.

A logical identity qualifies for the removal set as soon as it receives an engine application notification, without separate proof of error-free processing, complete application across targets or physical sources, or final modification effects. Partial, failed, skipped or unknown processing elsewhere must not disqualify that notified identity or preserve any of its matching occurrences. Entries whose logical identity received no application notification must remain. Notification collection must preserve the exact configuration resource path and original entry string; discovery, class-name equality or unknown attribution must not invent a key. Engine exceptions and Codev output-production failures still stop the affected production; they are not extra application-eligibility checks.

For every qualified identity, Codev must remove every physical occurrence with that exact resource path and original entry string from the Mixin arrays in all processed dependency copies. Matching must use exact equality of both values, without a source identifier, source path, hash or per-source uniqueness check. Repeated occurrences within an array, matches across `mixins`, `client` and `server`, and matches in different JARs must be removed together. A same-key occurrence in another physical source must also be removed even without separate confirmation of its application; this batch consequence is required and must not be rejected as source ambiguity. A different resource path or original entry string must not match. Entries with unqualified identities must remain.

`StripMixins` must perform this cleanup; a list alone must not require the user to implement the cleanup algorithm or JSON edits. The user or integration plugin must register, configure and consume it as specified below. For the Mixin-produced complete flow, notification eligibility determines the producer's set; independently, Strip's removal authority is the valid file supplied to `StripMixins.Parameters.removalsFile`, not an engine-notification proof. Actual parsing/DOM-access failures or inability to perform the required exact edit must fail cleanup by an outward exception, never silently claim completion; Strip must not add a separate input-validity pre-scan. A valid empty removal set or no matching entry must leave configuration content unchanged.

Cleanup must preserve remaining configuration fields and their values (including unknown DOM content), surviving entry order, other entries and unrelated archive resources. When an exact edit is needed, JSON formatting need not be byte-identical, but parsed DOM content outside the exact removals must remain semantically unchanged, subject only to the duplicate-object-key policy below. Mixin/helper classes, refmaps, whole configuration files (including ones whose explicit arrays become empty), Loader metadata and references must not be deleted or rewritten by this cleanup. In the Mixin-produced flow, a plugin/parent or dynamic contribution is not permission to invent an original explicit entry string or an engine notification; the producer still requires a notified exact logical identity.

Neither the named file outputs nor internal cleanup communication requires failure reasons, diagnostic or unknown-entry lists, status booleans, target-obligation arrays, source/classpath inventories, hashes, duplicate bindings/schemas or records paths. The runtime collection and entry file support exact batch matching, not complete-entry certification, and must not add a source identity or uniqueness condition to cleanup. Cross-loader values must meet the Accepted JDK/simple-value boundary and remain usable after the producing loader closes, without live engine objects.

### Entry file and JSON semantics

`Mixin.outputFile` must be the applied target JAR file output; `Mixin.appliedMixins` must be a second, tracked file output encoding the notified removal set. Its JSON object maps each **full configuration resource path** to a string array of **original Mixin-array entry strings**, read as a set of strings. For example, `{"configs/example.mixins.json":["Common","Client"]}` carries two exact keys for that resource, not class names expanded with a package. No source, proof, status or version fields are required. The child returns the corresponding materialized JDK Map/Set; the host writes this file after loader closure.

An empty object is a valid empty removal set; an empty array contributes no entries for its resource. Repeated strings in an array normalize to the same set member without changing all-occurrence removal semantics. The supported entry-file shape is an object of archive-relative configuration resource paths to string arrays; applicable configuration `mixins`, `client` and `server` fields, when present, are string arrays. These shapes describe the supplied data, not an obligation for Strip to hand-revalidate every root, value or element type. Strip trusts the supplied inputs and only filters those three arrays by exact configuration path and original string equality; it must not trim, normalize, expand or otherwise rewrite matching keys. It must not add name/whitespace/control-character checks, a character/path/business-validity pre-scan, a custom duplicate-ZIP-entry set or input size/CRC revalidation. Size/CRC required to write STORED output entries remain output-writing responsibilities. Actual parsing, DOM access, ZIP/I/O, writing and closure failures must propagate, and missing/unreadable files must not become an empty set. Strip guarantees neither rejection of every malformed input nor successful processing of bad input. The default UTF-8 decoding policy below and input/output protection remain applicable.

Codev JSON reading/editing must use the existing Kotlin serialization DOM, including metadata, configuration/parent, refmap and entry-file paths where applicable. **Duplicate keys within one JSON object follow the standard parsing semantics of the Kotlin serialization library version in use; Codev provides no additional guarantee of rejecting them.** This applies also to repeated configuration fields and unknown nested-object keys; it does not prescribe a fixed last-value policy or preservation of duplicate textual members beyond the library's DOM.

**Unescaped control characters U+0000–U+001F within JSON strings likewise follow the standard parsing behavior of the Kotlin serialization library version in use; Codev provides no additional guarantee of rejecting them.** Both syntax policies apply to all Codev JSON paths named above, including strings in unknown fields; Codev must not add a control-character scan of those strings. They do not waive applicable metadata/engine-input business rules or change the supported entry-file/configuration shapes; Strip follows the trusted-input boundary above without additional handwritten type, value or path validation. References to malformed or invalid JSON inputs in this Spec are subject to these two syntax policies and that Strip boundary. UTF-8 reading must use the installed library or engine's default decoding behavior, including replacement of malformed byte sequences where that decoder does so; Codev must not add strict decoding or a byte-validation scan. This applies to metadata, configuration/parent, refmap and entry-file JSON, including unknown fields. It guarantees neither rejection nor successful processing of every malformed byte sequence, nor a fixed replacement result across different readers. Native ReferenceMapper decoding/parsing and normally returned fallback remain engine-owned; this does not require every malformed input to become a default mapper. Other malformed metadata/engine inputs outside these syntax and decoding policies remain subject to the actual parser and native failure/fallback policy; actual Strip parsing/DOM-access failures must propagate without a separate validity-proof pass. Required metadata/engine business shapes, field types/values, string elements, archive-path validation and input protection remain in force. Do not retain `StrictJson` or build an equivalent syntax/duplicate-key/control-character scanner. These policies do not prescribe fixed edge-case results or imply equivalence to the preceding parser.

`StripMixins.Parameters.removalsFile` is source-independent: it may be connected to `Mixin.appliedMixins`, another task's output or a handwritten conforming file. Strip must read only the supplied set for its exact JAR edit; it must not load the engine, discover Loader metadata, require producer memory or require source identity, SHA or proof that notifications occurred. The file provider owns the business choice of the set. Strip must safely produce the exact edit under the trusted-input boundary above, but cannot promise to determine whether a handwritten set is semantically stale. Producer dependencies and current-input Gradle reuse still must not let failed or stale production stand in for current success. This independent capability does not broaden the same-operation complete-flow collection below.

## Pre-application Task and per-JAR Strip Artifact Transform

The selected structure is the **`Mixin` pre-application Task producer plus the per-JAR `StripMixins` Artifact Transform**, not an unresolved choice between a combined task, two tasks or a Transform. These names are retained; legacy all-delete semantics or full old API/ABI compatibility are not implied. Codev implements both components and performs real pre-application and exact strip; the user or an integration plugin registers, configures and composes them. `registerTransform` registration of the Transform type, parameters and from/to attribute rules is project-level configuration; the user or integration plugin also selects the consuming configuration or `artifactView`, requests the attributes and consumes the results. Codev is not responsible for automatic wiring, configuration selection or unified target/dependency delivery exits. Users must not have to implement the strip algorithm.

For each operation, the producer must read the supplied **raw target, raw Mixin sources and raw resolution inputs**, never its own strip view. For the complete cleanup flow, the user or integration plugin must organize the processing collection as exactly that operation's raw Mixin-source JARs plus its derived transformed target. Every JAR in that collection must go through the same per-JAR Strip Transform using that operation's qualified removal set; the derived target must also be stripped when it contains configurations before it can be described as cleaned. With no matching configuration or a valid empty removal set, the transform must preserve configuration content and unrelated resources. The raw target remains a protected producer input, not a substitute for its derived target in the cleanup collection.

For this Mixin-produced complete cleanup flow, the user or integration plugin's collection wiring must follow the operation's supplied raw collections and derived-target relationship. It must not expand cleanup to the entire runtime resolution classpath or an arbitrary external configuration, consume a stripped source as producer input, or union removal sets from different operations. An artifact present only for resolution is not a cleanup member unless it is also a supplied Mixin source. Collection wiring must not serialize source identity, freeze a source directory or copy sources into a new inventory. Repeated configuration paths/entry strings retain the exact all-match semantics above; necessary engine input-resolution validation is separate from strip identity.

The Task must expose `Mixin.outputFile` and `Mixin.appliedMixins` as its two tracked file outputs for downstream execution and normal cache restoration. For the complete flow, the user or integration plugin must bind the `appliedMixins` output provider to `StripMixins.Parameters.removalsFile` and preserve the producer references and build dependencies needed by the requested consumption. The entry file must carry the notified configuration-resource-path/original-entry-string sets and be usable without producer memory or a live operation loader. It is build data, not independent application records or an audit proof. A successfully produced valid empty set is distinct from missing, invalid or stale producer information: the latter must not be interpreted as empty, guessed from a target file or used to bypass required cleanup. Physical filenames, file ordering, provider wiring details, save/restore mechanism and cache algorithm are not frozen by the selected property names and encoding.

The caller may consume the Task's normally completed target output as an applied target; that output is not automatically a stripped target or proof that the cleanup flow completed. A caller requesting cleaned outputs must consume the corresponding Transform results, including the stripped derived target when it contains configurations, with the required producer dependencies. A failed, missing or unconfirmed required strip must propagate failure to that consumption and must not be reported as completion of the whole requested flow merely because another component produced a JAR. This does not require two Codev delivery exits gated together across all members, a transaction across arbitrary user tasks or a choice of downstream purpose.

## Build copy, completion and consumption

The two producers have independent file lifecycles, not a shared transaction, synchronized stage or common publication framework:

- `Mixin`: validate inputs and both output paths → create the isolated loader → process into a staged target and collect notifications → close archives, return the materialized JDK collection and close the loader → finish writing `appliedMixins` → complete both `outputFile` and `appliedMixins`. Neither file is a completed Task output before this sequence succeeds.
- `StripMixins`: read `removalsFile` → read the original JAR without modifying it and exactly edit matching configurations → write the Gradle Transform workspace → deliver only after owned resources close successfully. It does not invoke the Mixin engine or metadata handlers.

Each component's required validation and output-identity protection must precede destructive output actions; Strip's trusted-input boundary does not remove output protection or require a separate input pre-scan. A destination must not overwrite or alias any actual input, including real-path aliases, hardlinks or protected directory containment. Archive handling must not allow writes outside the owned output area; actual path-access or write failures must propagate. Input artifacts must remain untouched on every exit; non-transformed target entries/resources must be preserved in the build copy, and dependency resources must be preserved except for the exact configuration-entry removals above.

Engine invocation return, Task/Transform completion and availability for the caller's requested consumption are distinct boundaries. A normally returned engine transformation does not prove target writing, dependency cleanup or component publication succeeded. Identities qualify on notification, but the Task's internal cleanup information is available as a completed downstream input only after its own output production succeeds, including output writes, owned-resource closure, runtime exit and the Task's own publication. These physical production requirements do not certify complete or error-free Mixin application and must not become additional eligibility checks. Internal communication and staged data must not be advertised as completed component outputs or let the caller bypass processing required for its requested consumption.

Each Task or Transform must keep its writes staged/unavailable as its completed outputs until its own production or exact edits, output writes, owned-resource closure/exit and publication all succeed. Completed component outputs may feed downstream stages, valid build reuse or caller consumption for what that component actually completed; they do not establish completion of other components. Failure or unknown completion at any of those stages must prevent the affected outputs from being consumed as completed results. A cleanup failure must reach the caller and must not turn an already produced Task target into success for the whole requested cleanup flow. This is a component producer/consumer requirement, not an independent records protocol, a transaction across arbitrary tasks or a prescribed multi-file atomic rename.

The caller's consumption wiring must retain the required successful production/cleanup dependencies or obtain normally restored completed component results for the current inputs. For a flow requesting the transformed target and corresponding processed dependency copies, the caller must compose and consume those outputs; a cleaned dependency must not substitute for the target, and an unrelated old output path must not stand in for current completion. These component production and requested-flow obligations apply regardless of the user's intended purpose. They impose no use-based routing separation or Codev-selected downstream integration. The Task/Transform structure, same-operation processing scope and caller-owned registration, parameter binding and consumption are fixed. The named file properties and their roles are fixed; other task/provider API details and caller wiring mechanisms remain implementation choices. No unified operation-result object or aggregate delivery provider is required.

## Input changes, cache restoration and failure consumption

Gradle input/output tracking must cover every output-affecting input: target and Mixin-source contents, full ordered runtime resolution classpath including plugin method bodies/resources, effective side/options/settings, execution implementation dependencies, mapping contents/directional namespaces and selected refmap context. This includes inherited host system properties that actually affect output and their relevant unset/default states; internal observation must agree with Mixin's actual native reads. The original host values of `mixin.service` and `mixin.bootstrapService` are not effective native-option inputs because Codev fixes these selectors; input tracking must not capture another operation's temporary selector values. Their implementation is covered by implementation-classpath tracking. All other output-affecting native options and unset/default states remain tracked. Removing a public raw-override API does not remove these tracked inputs or make the whole unrelated JVM environment an input. The internal property carrier, enumeration, serialization and cache algorithm remain implementation choices. `@CompileClasspath` alone is insufficient for executable plugins. Changing only a plugin body, resource, configuration, mapping, effective environment or output-relevant host system property must produce a current-input result rather than reuse stale behavior.

Input/output tracking and normal reuse must cover the Task's produced target and cleanup-information file, each per-JAR Transform's parameters and input artifact, and its processed output. Each Transform must track the contents of its supplied `removalsFile` as an output-affecting input, with any necessary producer dependencies. In a Mixin-produced complete flow, that file must be the current operation's notified set, not a global or cross-operation union; caller-supplied registration and consumption wiring must preserve this tracking. A normal `UP-TO-DATE` or `FROM-CACHE` result must correspond to current tracked inputs and remain usable without the producing operation's in-memory state or a closed execution environment. Neither status executes this invocation's engine or supplies a fresh in-memory return; it must not be treated as new application evidence. The cleanup stage must obtain valid current-input internal information or reuse the correctly processed outputs for the whole required collection, including the derived target; a missing in-memory return is not permission to skip cleanup or guess removals.

File existence alone must not establish completion. Build dependencies and output tracking must prevent interrupted publication or a failed current producer from masquerading as valid reuse; old files must not substitute for a failed current result. Missing, invalid or stale internal cleanup information must prevent completed consumption rather than masquerade as a valid empty set, unless normal build execution/restoration supplies a valid current result. Consumers need not replay engine processing or verify an audit artifact. Beyond the selected file encoding and producer lifecycle, storage/restoration, component publication and diagnostic details remain implementation choices; caller-supplied wiring must preserve the required dependencies, and memory-only communication is insufficient. No independent records, additional manifest/sidecar or separate proof/persistence protocol is required. The current-producer/stale-result requirements concern production dependencies and reuse, not a provenance or age check for an independently supplied handwritten removal set.

Engine-thrown exceptions must propagate outward. Actual input-read/parse/DOM-access, transformation, dependency-cleanup, output-write or resource-closure/runtime-exit failures that prevent Codev from completing its output production, cancellation reported by an invoked API or a triggered configured timeout must throw an outward exception, stop the affected production and prevent consumers from receiving a current half-result or stale success. An interrupt flag alone does not require active detection or rejection of publication; the no-polling boundary above does not waive any actually reported failure. Logged engine errors, partial application or native plugin/refmap fallback with a normal engine return alone must not be converted into a Codev failure; invalid-input failure here is subject to that native policy without waiving required mapping/context or Codev business/I/O obligations. A previous output may physically remain, but a failed current invocation must not advertise or route it as current success, nor silently fall back to the untransformed target to pretend the requested flow succeeded. An incomplete owned publication must be removed or invalidated. Original inputs and unrelated inputs must not be deleted. No custom default timeout or restoration of an old output is promised.

A retry must use fresh operation state and, with identical inputs, agree semantically with a clean invocation. Output ownership must permit safe failure cleanup without deleting another operation's result. If Codev component production/publication, dependency-cleanup completion or current-input correspondence cannot be established, the affected outputs are not consumable; precise identities must not be fabricated to bypass that failure. Unknown Mixin application completeness is not such a production failure and must not remove a notified identity from the removal set. These are consumer-visible requirements, not a demand for digests, validation receipts or a new registration framework.

## Accepted interfaces and implementation boundary

The selected local technical structure is **accepted, not established as implemented or verified**:

- Retain `Mixin`, `StripMixins`, the two file outputs `outputFile`/`appliedMixins`, the source-independent `Parameters.removalsFile`, the resource-path → original-string-set file representation and materialized JDK Map/Set return. The complete Mixin flow and independent Strip input have the distinct responsibilities above. No full old ABI, fixed complete child-function signature, new versioned schema, file ordering or extra DTO is selected.
- The host owns Gradle tracking and Loader discovery; a fresh `IsolatingMixinClassLoader` runs the Kotlin whole-JAR child function, and the two producers follow their own selected lifecycles. Real loading/resource/SPI/input/failure protections remain mandatory without the old control, parser, SHA or publication frameworks.
- Mixin-specific listing/handler subinterfaces reusing Core signatures, resource/side reference snapshots, separate Fabric/Forge/NeoForge metadata adapters and explicit `remove` edits based on current metadata, without a public `removeConfigs` entry point, are selected. Strip must not call those metadata edits. All enum values, additional signatures and new null/empty-handler policies remain unfrozen.
- `GradleMixinRecorderExtension` supplies config and corresponding Mixin identity. Exact mapping back to original entries must be implemented, but attribution is not an unresolved architecture choice or a new proof gate. Notification alone qualifies an identity in the producer; it does not certify complete application. No target obligations, records, log judgment or engine-bytecode adaptation to prove all-target completion is required.
- Existing Kotlin serialization DOM and the library-version-standard policies for duplicate object keys and unescaped control characters within strings are selected. Default UTF-8 decoding and JDK resource-open failure semantics above are also accepted. These policies do not prescribe fixed edge-case results or relax metadata/engine business rules or input protection. Strip's accepted trusted-input boundary removes extra handwritten validation, not exact array-set/all-match semantics.
- Other task/provider API details, caller wiring, private physical filenames, completion/storage/restoration details and cache algorithms remain implementation choices within the fixed file interfaces and lifecycles. No registration helper, aggregate provider, two unified delivery exits or separate proof platform is required. Caller registration, parameter binding, same-operation collection scope, attribute requests and consumption remain explicit; downstream purposes/routes belong to the user.

Document acceptance is not evidence of new-design execution or acceptance. The user has separately authorized document alignment and Work/Context/Plan/Waves preparation; this update does not perform that preparation or create/confirm a ready Plan. Production implementation, code removal and consumer rewiring still require separate confirmation. The accepted isolation core is retained, and old G1 remains historical accepted/closed delivery rather than new-design evidence. Existing scoped implementation and partial results retain their recorded meaning: this text neither resets them to unstarted nor upgrades them to completed, releases a Wave gate or proves these simplifications implemented. Same-identity ADR follow-through concerns Core reuse, separate metadata ownership, native failure boundaries and the selector window/global-property limitation. The existing redesign Plan/Waves must reconcile affected interfaces, resource/codec placement, remapper references, selector tracking and focused checks within their own scope; this Spec update does not edit or approve that graph.

Exact dependency configuration-entry cleanup and the retained `StripMixins` name are required; old API/DSL/ABI/processor-registration compatibility or legacy all-delete semantics, runtime contribution suppression, whole-configuration deletion and Loader metadata rewriting are not. Neither are independent records/schema/digests/native obligation arrays, old-format migration, binding proofs, consumer replay or a replacement verification manifest/receipt framework. This does not authorize deleting their existing implementation. Unrelated cache/lock/remapper/includes/launch/IDEA redesign, old Core test restoration and support-matrix expansion remain outside scope. Existing AW/class-tweaker, Fabric AW, Forge AT/patch and nested-JAR behavior on touched paths must not be regressed; this is not a redesign or new certification of those capabilities.
