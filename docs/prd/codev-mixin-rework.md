# Codev Mixin Rework

**Status: Active.** The [Chinese translation](./codev-mixin-rework.zh-CN.md) describes the same product target.

## Problem, user and outcome

The user (the party invoking this build capability) needs a build-time copy of Minecraft processed by the real Mixin engine with the specified Mixins. Codev provides and executes real pre-application and exact configuration-entry cleanup. In a complete cleanup flow registered and composed by the caller, the consumed target must be the usable output of real engine processing, and the processed configurations must no longer contain entries whose logical identity received an engine application notification. Codev does not additionally prove error-free or complete application. Completed component outputs may be consumed for what that component actually produced; an applied target alone does not establish cleanup completion. Independent operations must not affect one another; logs and exceptions make processing and failures observable.

Codev does not restrict who consumes the output or whether it is used for compilation, decompilation, packaging or running. The user decides its use and integration; these examples are not a support matrix or a guarantee of compatibility or safety for every downstream use.

## Product requirements, in build order

### 1. What the user supplies

**R3 — Correct inputs.** The user specifies the target JAR, the sources containing Mixin configurations and classes, the dependencies needed to resolve them, any task plugins and resources, and the intended environment (such as client/server), with necessary naming mappings and refmap context as required by R8. General engine options follow Mixin's native host system properties and default behavior; Codev neither reinterprets those options nor provides independent per-task overrides for them. Codev must use those inputs consistently; host or Loader dependencies must not silently replace the intended execution components. Ambiguous required engine input resolution or unusable inputs must produce a clear failure rather than a guessed selection; plugin/refmap availability follows R6 without relaxing R8. Repeated cleanup identities across input artifacts are not, by themselves, invalid inputs.

**R8 — Names resolve correctly.** When the supplied inputs use different names for the same classes or members, the user supplies the necessary naming mappings and an explicit source → target direction, plus the refmap context when needed. A refmap is a resource used to resolve names referenced by Mixins. Codev must reach the intended class, method or field without confusing owners, overloads or descriptors. Inputs that already use compatible names need no mandatory mapping. Invalid mappings, unavailable explicitly requested contexts and required resolution failures must be visible failures, not arbitrary matches.

### 2. How Codev processes them

**R2 — Independent operations.** Each operation works on a build copy with its own execution state. A successful, failed or cancelled operation must not leave Codev-owned configuration, plugin or mapping state that changes another operation. Independent concurrent operations must agree with serial execution, and conflicting output destinations must not mix results. Codev must release the resources it owns and leave retries free of previous operation state; this is not a sandbox for arbitrary plugin side effects.

**R4 — Real application.** Codev uses the real Mixin engine to transform the specified target and records the application notifications it provides. Discovering a configuration or finding a candidate alone does not qualify an entry for cleanup; an engine application notification does. Codev does not independently verify injection semantics, error-free processing or completion across all targets, and does not parse engine logs to determine success or recreate the engine's validation obligations. The engine outputs logs for the user to read. Completion of Codev's output production does not assert that every requested application succeeded.

### 3. What Codev delivers and cleans

**R5 — Deliver applied targets and cleaned dependency copies.** When the caller registers, composes and requests a complete cleanup flow, Codev must execute real pre-application and exact configuration cleanup. The consumed target must contain the output of real Mixin engine processing, and the processed configurations must no longer contain entries whose logical identity received an engine application notification. The caller must select and consume the corresponding cleanup results for all required copies, including the derived target when it contains configurations, rather than treat an applied target as already cleaned. Codev implements the cleanup algorithm; the caller configures and connects the capabilities, not a replacement cleanup implementation. The logical cleanup identity is the full configuration resource path plus the original string in its Mixin array, before package expansion or name mapping. An engine application notification qualifies that identity for removal without separate proof of error-free processing or complete application across targets or physical sources. Partial application, logged errors or unknown completion elsewhere do not disqualify a notified identity; exceptions and output-production failures still propagate as required by R6.

For each qualified identity, Codev removes every matching physical occurrence from the Mixin arrays in all processed dependency copies, including repeated entries, occurrences in different arrays and occurrences in different JARs. No source identifier, source path, hash or per-source uniqueness check participates in cleanup matching. This also removes a same-key occurrence from another physical source without requiring separate completion for that occurrence. Entries whose identity is not qualified remain; equal class names alone do not match entries with a different configuration resource path or original entry string. Remaining fields and values, including unknown fields, surviving entry order and unrelated resources must be preserved. Mixin classes, refmaps, configuration files and Loader metadata remain intact.

### 4. Who receives the output

Codev provides pre-application and configuration-cleanup capabilities for the user or an integration plugin to register and compose. Codev implements and executes both capabilities; the user or integration plugin registers and configures them, connects their inputs and outputs, and selects which dependency configurations consume the transformed results. This does not require the user to implement cleanup, or Codev to register the capabilities automatically, select consuming configurations or provide unified delivery routes.

**R10 — User-directed use, completed outputs.** The user decides who consumes the completed transformed target and processed dependency copies and for what purpose. Codev must not impose a compilation/decompilation-only restriction, prohibit packaging or running, or require separation of consumer routes by use. This does not guarantee every downstream use is compatible or safe, or require Codev to choose or implement those routes.

The original target and Mixin-source artifacts remain unchanged; dependency configuration cleanup occurs only in separate copies. Codev remains responsible for each component's completed production and exact cleanup, regardless of later use. Completed component outputs may be consumed for their actual results; the caller must compose and consume all required cleanup results to obtain a complete cleanup flow. A normal engine or producer return alone does not establish component publication or completion of the requested cleanup flow.

Every output-affecting input must participate in build input/output tracking, including configurations, classes, plugins/resources, dependencies, environment/options and any mappings used. Changed inputs must produce results for the current inputs. Normally cache-restored component results must correspond to current inputs and remain usable without the producing operation's in-memory state. Restoring an applied target alone does not complete cleanup: the caller's requested complete cleanup flow must execute or correctly reuse all required cleanup results with their production dependencies intact. A stale result must not stand in for a failed current build.

### 5. How failures are handled

**R6 — Honest diagnostics and safe output.** Exceptions thrown by the engine, invalid inputs, cancellation, and transformation, dependency-cleanup or output-write failures that prevent Codev from completing its output production stop the affected production by an outward exception and prevent its partial or stale results from being consumed as current success. Engine exceptions must not be swallowed. Required cleanup failure must propagate to the affected consumption and must not be reported as success of the requested cleanup flow; it does not negate an independently completed applied target or require a transaction across arbitrary caller tasks. Original inputs must never be overwritten; invalid archive paths must not permit writes outside the intended output.

When the engine logs errors or only partially applies Mixins but returns normally, this alone neither fails Codev's output production nor disqualifies notified cleanup identities. Plugin/refmap availability follows the engine's native required/optional and fallback behavior: when the engine handles an unavailable plugin or refmap by returning normally, including with a default mapper, Codev must not independently turn that outcome into a failure. This does not waive R8's naming-mapping or explicitly requested refmap-context requirements. The engine's logs are available for the user to read; Codev does not interpret them to judge application success. Completed output must not be presented as proof that every requested application succeeded. Codev's own failures must be observable through logs or exceptions identifying the failing stage, relevant configuration or target when known, and the underlying cause; unavailable attribution remains explicit uncertainty, not an invented identity.

### Expected flow example

The user supplies a Minecraft JAR, a dependency mod's Mixin inputs, resolution dependencies and any needed naming mappings, and registers and composes the capabilities for a complete cleanup flow → Codev invokes the real Mixin engine on a separate build copy and qualifies cleanup identities as it receives engine application notifications → the caller connects the produced cleanup information to Codev's cleanup capability and selects the consuming dependency configurations → Codev removes every occurrence of those configuration-path/original-entry-string pairs from the required copies, including the derived target when it contains configurations, while retaining entries with unqualified identities → the caller consumes the corresponding completed target and cleaned dependency results and decides their use, without implementing the strip algorithm. The user reads the engine's processing and failure logs. Cleanup follows application notifications, not additional proof of complete or error-free application or the user's intended downstream use. An exception or failure preventing Codev from completing its output production stops the affected build rather than supplying half-finished outputs; partial application or logged errors with a normal engine return do not by themselves constitute such a failure.

## Scope limits

The capability covers real Mixin pre-application, exact dependency configuration-entry cleanup, completed-output delivery and diagnostic visibility. Downstream integration, runtime reapplication prevention and packaging/distribution guarantees are outside scope. Logs and exceptions provide diagnostics; structured diagnostic returns, independent records and consumer replay are not required.

Unrelated build-system redesign, automatic engine upgrades, new extension or Loader support guarantees, and broad compatibility matrices are outside scope. Concrete APIs, task structure, internal communication, output layout and cache mechanisms are technical choices rather than product requirements.

## Observable acceptance

Acceptance uses small real-engine class/JAR examples and focused checks of the user's build flow; downloading or launching a game is not a prerequisite.

- **AC3 — Supplied inputs are used (R3).** An operation uses the specified configuration, classes, dependencies, environment and task-plugin resources, without silent host replacement. Ambiguous required engine input resolution or unusable inputs fail clearly, subject to R6's engine-native plugin/refmap policy without relaxing R8; repeated cleanup identities alone do not fail validation. Changing an output-affecting input produces the corresponding current result rather than reusing a stale output.
- **AC9 — Correct names (R8).** A real application requiring mappings reaches the intended member, including same-name members with different owners or overloads. An application with already compatible names works without mappings. Invalid mappings, unavailable requested contexts or required name-resolution failures provide no falsely successful output.
- **AC2 — No cross-operation state (R2).** After an operation with configuration/plugin/mapping state, another operation with different inputs has no leaked behavior, including after failure and retry. Independent concurrent results agree with serial results; conflicting destinations do not combine outputs, and owned resources are released.
- **AC4 — Real results and failures (R4, R6).** A successful real injection is visible in the completed output. Discovery or candidate callbacks alone do not qualify cleanup identities. When the engine returns normally with partial application or logged errors, its logs remain available for the user to read; Codev does not independently validate injection semantics, parse logs to judge success or require proof of complete, error-free application. Output completion is not reported as proof that every application succeeded. An unavailable plugin/refmap handled normally by the engine's native required/optional or fallback behavior, including a default-mapper return, must not be upgraded to a Codev failure; R8's mapping/context requirements remain. An engine exception, invalid input outside that engine-native policy, cancellation or failure preventing Codev's output production raises an outward exception, stops consumption of a current partial or stale result and provides the stage and underlying cause, with affected identities when known.
- **AC5 — Exact dependency cleanup (R5, R4, R6).** In a caller-registered and composed complete cleanup flow, the caller consumes the corresponding cleanup results for all required copies, including the derived target when it contains configurations. The consumed target contains the output of real engine processing, and the corresponding processed configurations no longer contain entries whose logical identity received an engine application notification. Codev executes the cleanup algorithm; an applied target alone or a removable-entry list does not satisfy this complete-flow condition. Include an entry with multiple targets: once its logical identity receives an application notification, remove all matches even if another target or physical occurrence failed, is incomplete or has unknown completion and the engine returns normally. No additional proof of error-free or complete application is required to qualify the identity; engine exceptions and Codev output-production failures still stop the affected production. Match by full configuration resource path plus original Mixin-array entry string: remove all matching physical occurrences across arrays and JARs together, without a source identifier, source path, hash or per-source uniqueness check, even when an occurrence in another source has no separate completion confirmation. A different configuration path or original entry string does not match; entries with unqualified identities remain. Cleanup preserves remaining fields and values (including unknown fields), surviving entry order and unrelated resources, and leaves original artifacts unchanged. Logs or exceptions expose failures.
- **AC11 — User-directed use and cache safety (R10).** Codev imposes no consumer-identity or output-purpose restriction and does not require use-based route separation; downstream routes remain the user's decision, not a promise of arbitrary downstream compatibility or safety. Original inputs remain unchanged. Normal engine or producer return alone must not establish component completion before that component's production and publication succeed. A normally completed pre-application target may be consumed as applied, but not as stripped or as completion of the requested cleanup flow. Required cleanup failure propagates to the affected consumption without negating another independently completed component. Normally cache-restored component outputs are usable without producer memory and correspond to current inputs. For a requested complete cleanup flow, the caller consumes all corresponding cleanup results, including the derived target when it contains configurations; the required entry cleanup remains complete after normal execution or valid cache reuse.

## Dependencies and risks

The [operation-isolation ADR](../adr/mixin-operation-isolation.md) defines the Accepted operation-local architecture. The [Spec](../spec/mixin-preapplication.md) defines technical processing and delivery contracts for this product target.

The user has accepted the [three-diagram design](../design/mixin-design.html), and the original English and Chinese Specs have been aligned with that accepted structure. The selected invocation structure, input/output representation, application-notification contact point, internal communication and producer completion boundaries are defined in the [Spec](../spec/mixin-preapplication.md); remaining implementation details are choices within that contract, not wholly undecided design. Codev's responsibility for implementing pre-application and cleanup, the user's or integration plugin's responsibility for registration, composition and consumption selection, and notification-based cleanup eligibility and all-match removal remain unchanged. This round of reimplementation, verification and acceptance has not started; historical implementation and verification remain historical facts, not evidence that the accepted new design has been implemented or passed acceptance.

The main risks are mistaking unrestricted output use for guaranteed downstream compatibility or safety, or treating application notifications as proof of complete, error-free application. Notification-based batch matching deliberately removes same-key occurrences across physical sources and targets even when some applications are partial or unconfirmed; entries without a notified identity remain. The user must read engine logs to assess application issues. Accurate notification recording, visible diagnostics and safe completed outputs remain essential.
