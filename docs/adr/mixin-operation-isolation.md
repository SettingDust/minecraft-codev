## Context and decision drivers

The following source observations and selective drivers describe H and the old G1 preparation, not newly verified implementation or current-target integration.

Codev already pre-applies Mixin at build time. In H, the Gradle plugin bootstraps Mixin during `apply`; `GradleMixinService` retains a lazy transformer, and each `use` clears selected configuration collections while sharing the environment. The source does not demonstrate that clearing those collections resets processor state, class metadata or extension state. The same service constructs a task URLClassLoader without closing it, resolves ordinary classes through host `Class.forName`, and reads bytecode/resources through the task loader with an external-file fallback. These are inspected source facts; cross-operation contamination and mismatched host/task dependencies are static risks, not failures newly reproduced here. [S4]

The task marks executable `classpath` inputs as `@CompileClasspath`, although plugin bodies and resources can affect execution. It discovers configs from `mixinFiles` and the input target, then writes transformations directly to the output archive. Its archive-class-name conversion uses the host file separator. These facts force attention to declared runtime inputs, task-owned resolution, Windows ZIP paths, and publication/resource ownership within G1; they do not justify a shared-cache or launch-system redesign. [S4; S2, C2–C3]

The existing `StripMixins` deliberately deletes all listed configs and calls a shared handler's all-delete `remove`. That behavior remains useful and is not selective preservation. A new selective consumer needs completed application evidence tied to both the transformed target and the original configuration-bearing artifact, which can be a different JAR. Historical F (`45b8a58d13c30b017060a99f8a7e1b647ad16902`) supplies an isolation precedent, but its target-level recorder and text/name-only cleanup or mapping cannot establish this stronger contract. [S5–S6; S1, §§2–4/E6]

The assessment reports that the locked `net.fabricmc:sponge-mixin:0.15.0+mixin.0.8.7` already has the refmap/environment-remapper chain. Its earlier optional-failure investigation uses 0.17.0 source plus the 0.15.0 binary surface: a target's candidate mixin set at `postApply` is not proof that each candidate completed. The later exact-version scratch proof narrows the success-mechanism uncertainty for one native-exception scenario: Good completes on the same target where optional Bad fails, and reconciliation identifies only Good after transformation. It also finds Bad's merged handler still in the output. Exact non-completion therefore does not establish rollback or safe runtime retention. A dependency upgrade is neither a mapping prerequisite nor a substitute for complete success and selective-safety evidence. [S1, E7–E9; S7; S10; S2, C4–C5/A4/A7]

The retained architecture prioritizes independent operation state, coherent class/resource identity and honest completed-result diagnostics. Preservation of unconsumed runtime behavior and existing API compatibility were additional drivers of the historical selective scope, not requirements of the current target. The [Spec][spec] now owns target-aligned detailed behavior and failure contracts, including the accepted local structure and its remaining implementation choices; this ADR owns the same accepted architectural choice, its rationale and historical applicability.

## Decision

Operation-owned execution, task-owned resolution and locked-engine mapping below retain the accepted architecture. Spec citations identify the contracts used at adoption; they do not carry forward excluded compatibility/records/cleanup obligations. The separately labeled selective section preserves the historical decision and rationale only. Public interfaces and detailed failure/consumption contracts belong to the Spec, not duplicate normative surfaces here.

### Operation-owned execution

Create a fresh runtime classloader for each operation and close it on every exit. Define the Codev execution implementation, the selected Mixin engine and ASM as one coherent implementation set inside that operation. Its bootstrap, Codev service/global-property state, environment, transformer, configuration registration, class metadata, remappers, recording state, extensions and task-plugin static state have the operation's lifetime. Applying the Gradle plugin configures Gradle surfaces; it does not bootstrap a shared transform environment. The selected realization follows the historical operation-loader direction while correcting the ownership gaps identified in H and F. [S1, §2/E4/E6; S2, C2]

Within that decision, the host `Mixin` Task owns Gradle parameters, input/output and cache tracking, and Fabric/Forge/NeoForge configuration-reference discovery. Each invocation creates an `IsolatingMixinClassLoader` that loads a real Kotlin child function to parse configurations/mappings, initialize the engine, process the whole target JAR into a staged copy and collect notifications. After closing its archives, the child returns fully materialized JDK Map/Set values carrying configuration resource paths and original entry strings; the host closes the loader before finishing the entry file and completing both named Task outputs. This Kotlin-first seam uses the existing Kotlin serialization DOM inside its loading domain, not across the boundary. Ordinary Kotlin/NIO, existing JAR/loader APIs and scoped `use` own resource access and closure; serialization belongs to host output writing and Strip input/editing. No separate resource/codec layer or same-shaped replacement is needed. It requires no `EngineOperation` control layer, `StrictJson` or equivalent scanner, custom engine-JAR SHA allowlist or generic `OperationPublication` framework; removing those prerequisites does not remove real loading, dependency tracking, SPI/resource ownership or failure protection. The [Spec][spec] owns interface and lifecycle details.

Use the existing Mixin service SPI within this domain, selecting Codev's service and global-property implementation. Task dependencies must not replace an arbitrary part of the implementation set or supply a competing Fabric/Forge Mixin service. The selected realization uses native `mixin.service` and `mixin.bootstrapService` selectors during a short initialization window, not loader-synthesized service-resource redirection. Before child engine initialization, participating Codev operations/host copies share one JVM-wide initialization exclusion boundary, save both original selector values or unset states, temporarily select the child-domain Codev service/bootstrap, initialize and cache the child service, and install/cache an operation-owned child global-property service. `IGlobalPropertyService` has no native selector; the two properties alone do not install it. Its private integration remains a locked-engine adaptation point, without freezing reflective field names or a monitor contract. [Current Spec][spec]

Restore both selectors in `finally`, including failure or cancellation, restoring an originally unset value to unset. Restoration failures propagate with any earlier cause preserved. Release the short exclusion only after restoration; do not lock the whole transformation. Cached child services and mutable state remain operation-owned, allowing independent transformations to overlap. This chooses no property-lease or general locking framework. Other nonparticipating hosts may observe or interfere with temporary selector values; the window is not an arbitrary-host sandbox.

Track output-affecting inherited settings and their relevant unset/default states while retaining Mixin's native host-system-property/default option semantics, without per-Task raw overrides, independent option snapshots or Codev reimplementation of option inheritance/parsing. The fixed service/bootstrap selectors' original host values are not effective native-option inputs; tracking must not capture another operation's temporary selector values. Implementation-classpath tracking covers their implementation, while all other output-affecting native options and actual execution dependencies remain tracked. The SPI registrations existed in H; the preceding adoption did not verify operation-local selection at preparation, and this refinement is not new implementation evidence. [S7; S2, C2–C3; current Spec][spec]

Cross the loader boundary with JDK types/simple values, including the effective side value; do not cast Mixin or ASM instances from incompatible loaders. The historical public Side type and compatibility commitment are recorded by Spec C1, not imposed on the new interface by this ADR. Restore any changed thread context classloader in `finally`. Close owned loaders, streams and ZIP filesystems after success, failure or cancellation. Distinct operations own independent temporary locations and mutable state; processing targets sequentially within an operation remains valid. The Task's two outputs must be physically distinct. Conflicting producer destinations need exclusive ownership or rejection through completion; multiple readers of a completed output are not conflicting producers. This requires neither a generic lock framework across independent builds nor a multi-file transaction and does not promise parallel speedup. [S2, C1–C3]

### Task-owned resolution

Give ordinary application classes, task plugins, their dependencies, class bytes and resources one task resolution domain with the declared precedence `classpath → mixinFiles → inputFile`, preserving order within each collection. Platform classes and the coherent implementation set retain their defined domains. Host-only application classes must not win while the corresponding resource comes from task inputs. This is an explicit domain policy, not blanket child-first loading for every JVM class. [S1, §2; S2, C2]

Keep configuration discovery limited to `mixinFiles` and `inputFile`; merely placing a config on the ordinary classpath does not register it. Resolve discovered configs, plugins and refmaps from declared inputs under the defined precedence. Outside engine-native required/optional/plugin/refmap handling, genuinely ambiguous required engine input resolution must fail rather than guess; repeated configuration resource paths or cleanup identities across JARs alone are not invalid and require no per-source uniqueness check or origin-record artifact. Resource access must be input-accounted: an intentional external-file facility would require tracked contents; implicit working-directory or host-classpath fallback is not a reproducible resolution source. Archive class names use ZIP `/` segments on every host. [S2, C2–C3; current Spec][spec]

Host discovery uses Mixin-specific `MixinListingRule : FileListingRules` and `MixinConfigHandler : ListedFileHandler` subinterfaces, reusing Core signatures without expanding Core or Jar-in-Jar into a Mixin framework. Core listing/removal concerns references and their declarations, not necessarily physical JAR deletion. Handlers retain a `MixinConfigReference` resource/side snapshot, not a separate `environments` capability. Fabric owns JSON metadata; the Forge module's separate Forge and NeoForge adapters own Manifest `MixinConfigs` and `META-INF/neoforge.mods.toml` respectively. Discovery visits all applicable rules, including both formats when present, without a combined handler, cross-format set-equality requirement or TOML extension fields reinterpreted as Fabric side.

Explicit `remove(root: Path)` edits retain real current-metadata editing; `MixinConfigHandler` must not expose a public `removeConfigs` entry point. Each adapter parses/validates its business fields at actual load/edit boundaries and edits only its owned format, preserving unrelated and unknown content and references added after the snapshot. Snapshot age alone is not an edit failure. Do not add a separate duplicate pre-read/reference-validation pass; adapter-owned TOML load/save/close failures propagate. The new Strip neither discovers Loader metadata nor calls these edits. Removing the public entry point has source/binary compatibility consequences; out-of-repository callers are unknown, so absence of compatibility impact must not be claimed. This is the accepted target interface, not evidence that code removal or verification is complete. This retains format ownership and real editing without redesigning Core; the [Spec's configuration discovery and handlers section](../spec/mixin-preapplication.md#mixin-configuration-discovery-and-handlers) owns signatures and detailed behavior.

The child performs the original-entry reads needed for notification keys, including parent traversal as needed, side/mapping setup, registration and real transformation, preserving target-JAR `@Mixin` definitions. It does not duplicate DOM reads for pre-validation, pre-scan every declared class/plugin/refmap for existence or same-JAR origin, independently validate parents or inspect all configurations after transformation to revalidate native decisions. These extra checks would duplicate engine policy and could turn permitted fallback into Codev failure; moving them to a helper would not change that conflict. Actual reads, default UTF-8 decoding, business shapes and paths, necessary mapping/explicit context selection, notification-to-key mapping, cancellation reported by invoked APIs and genuine engine/I/O/close failures remain responsibilities, subject to the native fallback and loader-open boundaries below. [Current Spec][spec]

Within this same accepted decision, UTF-8 JSON reads use the installed library or engine's default decoder, including replacement of malformed byte sequences where that decoder does so. This covers metadata, configuration/parent, refmap and entry-file JSON, including unknown fields; Codev adds neither strict decoding nor a byte-validation scan. The choice avoids a separate decoding policy layered over the installed readers. It guarantees neither rejection nor successful processing of every malformed sequence, identical replacement across readers, nor a default mapper for every bad refmap. Native ReferenceMapper decoding/parsing and normally returned fallback remain engine-owned. Existing business-input rules, Strip's trusted-input boundary, exact logical-key/array matching and input protection remain as specified in the [English JSON contract](../spec/mixin-preapplication.md#entry-file-and-json-semantics) and its [Chinese counterpart](../spec/mixin-preapplication.zh-CN.md#条目文件与-json-语义).

At the loader resource-open boundary, use JDK `getResourceAsStream` semantics: an opening `IOException` may become `null`/resource unavailable without its original cause. Do not add an open wrapper or pre-read solely to recover that cause. Required-input unavailability still fails clearly; native optional plugin/refmap unavailability may follow normal engine fallback. This deliberately accepts the JDK's diagnostic limit in exchange for direct use of the existing loader API. It covers opening only, not read/close faults after obtaining a stream, direct file/JAR I/O, output writing or selector restoration. Preserve available causes, including through reflective wrappers; native internally caught exceptions with normal fallback remain engine-owned, without authorizing Codev to catch and ignore failures. The [English resolution contract](../spec/mixin-preapplication.md#supplied-materials-and-resolution) and [Chinese resolution contract](../spec/mixin-preapplication.zh-CN.md#提供的材料与解析) own the detailed boundary.

### Completed result and selective evidence

**Applicability: the following records-consuming/selective-runtime policies were accepted for the old compatible/selective G1 delivery only.** They remain history and rationale, not requirements or selectable defaults for the current target. Selective-ready rejection is not ordinary engine failure policy: an engine-permitted optional failure may coexist with completed output and honest logs, while its failed/incomplete/unknown entry remains non-removable. Current dependency configuration-entry cleanup is build dependency processing, not runtime contribution suppression or a safe-reapplication guarantee. The [Spec][spec] owns completed real application and exact dependency cleanup. The materialized JDK collection is internal communication, not a public completion product; `Mixin.outputFile` and `Mixin.appliedMixins` are the two required tracked Task file outputs, not optional in-memory delivery. Source-independent Strip reads a valid `Parameters.removalsFile`, whether connected to `appliedMixins`, another task or a handwritten file, without engine/metadata discovery or notification proof. The file provider owns that set's business choice; Codev retains format/path validation and safe exact edits. This independent capability does not expand the Mixin complete flow beyond the same operation's raw sources and derived target or relieve caller binding and consumption. The producers have independent completion lifecycles, not a shared transaction. No independent records or diagnostic return is required. Input tracking, resource ownership and completion correctness still apply: each requested component must complete its own production, owned-resource closure/exit and publication or valid current-input reuse before consumption as completed. A normally completed Task target may be consumed as applied, not as stripped or as completion of a requested cleanup flow; the caller must consume all required Transform results for that flow, and required cleanup failure must propagate to the affected consumption.

Treat the transformed target and application records as one logical completed result. Stage them until transformation, serialization and applicable selective-safety checks succeed; consumers validate completion and content/scope binding. Interrupted publication, failed producers, retry or cache restoration must not make stale records or a half-result consumable as current success. A completion boundary is required, without prescribing a public manifest protocol or filesystem-level atomic rename of multiple files. Full ordered runtime classpath contents, effective options, mapping inputs and consuming artifacts participate in Gradle input tracking. [S2, C3–C4]

Record exact successful mixin/config-origin/target identities with the completion obligations required by C4. Isolate any version-sensitive success instrumentation in the locked-engine adaptation point. Config discovery, candidate sets, entry into target `postApply`, audit `onApply`, the early-set `applied` flag, a bytecode difference or an absence of exceptions alone cannot authorize success records. A per-mixin success hook or reconciled engine success state must distinguish engine-permitted optional failures. Target callbacks provide provisional identities only; promotion requires a normally returned transformer and committed output under C3, with real config-origin/target associations rather than a cross-config name set. Separately retain attempted-failure identities, stage/cause where known, and known residual mutations or explicit unknown effects. If reliable attribution or completion cannot be established on the locked engine/path, selective-ready production fails explicitly; precision is not fabricated. Ordinary execution retains the engine's required/optional semantics and may produce ordinary evidence without claiming selective readiness. [S1, §3/E6/E9; S2, C3–C4; S10]

The bounded pinned-engine reconciliation was an evidence-backed provisional mechanism candidate at preparation: at `IExtension.postApply(ITargetClassContext)`, reconcile the retained private `TargetClassContext.mixins` members with `getSuppressedExceptions()` and each native failure's `getMixin()` identity. The exact-source/binary control-flow cross-check and actual Good/Bad run support this subtraction for that scenario; callback state still precedes processor post-processing and output generation. The released binary lacks the source JAR's `getMixins()` method, so its verified private field/method surface needs a version-bound adapter. This is not a mandatory public reflection protocol or proof of every failure path, complete obligations, C4/A4/A7, publication or isolation. [S10; S2, C4 and pinned-engine evidence P1–P2]

The historical compatibility choice kept existing Mixin conventions/no-mapping calls and the explicit legacy all-delete `StripMixins` operation, adding a separate records-consuming selective entry point rather than changing the old meaning. Spec C1 records the exact old signatures, registration and unsupported-handler behavior. Mixins owned the local selective capability and records; Fabric/Forge owned metadata adaptation, avoiding a broad core `ListedFileHandler` ABI change, generic core serializer or reverse dependency. This explains the old adoption cost and module seam; it mandates neither preservation of those entry points nor a new cleanup interface for the current target. [S1, §§3/6; S2, C1; S5–S6]

The historical cleanup decision removed only exact contributions proven completely consumed, retaining independent wholly untouched entries and metadata/resources without ownership proof. A missing success record did not prove untouched state; empty arrays did not prove runtime exhaustion. Plugin/parent retention and all applicable metadata references needed the same safety boundary, with Fabric/Forge owning adaptation. Detailed JSON identity/preservation and Forge token/NeoForge TOML rules belong to Spec C5–C6 rather than duplicated normative text here. These historical runtime-safety policies do not define current dependency configuration-entry cleanup: Codev removes all occurrences matching engine-notified logical identities from dependency copies, not classes, refmaps, whole configuration files or Loader metadata. [Spec][spec] owns that current boundary. [S2, C4–C6]

For an attempted failure with zero successes, retention requires supported evidence of no residual modification in the committed output and safe runtime retention across all applicable obligations. Known residual mutations, unknown residual effects or unproved retention safety reject selective publication, even when that entry has no successes. Neither retaining nor deleting it is a safe default. The same-target Good/Bad proof illustrates why: Bad did not complete but its handler remains merged. Whole-target byte equality alone cannot prove per-mixin independence or safe reapplication when other mixins affect that target. The adopted policy supplies no rollback or general runtime-suppression machinery; ordinary optional failure remains engine-permitted. [S10; S2, C4–C5/A4/A7]

If one mixin succeeds on some targets but has unsuccessful or unknown remaining obligations, reject the selective result. Retaining that entry could reapply it to an already changed target; deleting it could lose its remaining behavior. Apply the same adopted failure default when a retained plugin/parent or dynamic contribution can re-supply a pre-applied mixin and suppression cannot be proved. Empty explicit arrays do not prove exhaustion. A plugin/parent config with no pre-applied contribution and no unsafe failed attempt may remain untouched. No generic runtime target-exclusion adapter or proof of arbitrary plugin behavior is part of this default; legacy ordinary execution/all-delete APIs do not acquire these selective restrictions. [S1, §3; S2, C4–C5]

### Optional mapping through the locked engine

Retain `net.fabricmc:sponge-mixin:0.15.0+mixin.0.8.7`. Use a mapping-io adapter, with `0.7.1` as the repository precedent, in the engine's existing `refmap(reference) → MemberInfo → environment remapper chain` path. There is no dependency on the whole Codev remapper service or G4 reuse architecture. The assessment supplies static chain evidence; this ADR does not assert that an adapter or runtime fixture has been implemented. [S1, §4/E7–E8; S2, C7–C8; S7]

Mapping mode remains optional. Inputs already using compatible names need no mapping. Retaining effective engine settings and avoiding unconditional `REFMAP_REMAP` is the adopted default, not a commitment to the old public invocation surface. When mapping is requested, validate complete mapping/source/target inputs before output writes. The source namespace describes selectors after refmap resolution; the target namespace describes input target bytecode. Refmap context is separate from namespace; do not guess direction or alias `official` to `named`. Ordinary no-refmap/default-mapper cases remain valid. [S2, C7; S8]

Locate members by source `(owner, name, descriptor)` and obtain the target name from the same entry; map classes and descriptors in the same direction and reverse/unmap in the opposite direction. Missing mappings/null target names pass through, and null member names stay null. Incomplete identity permits a rename only when uniqueness is proved; otherwise preserve the selector with an ambiguity diagnostic and let normal engine matching/required handling run. No first-name scan, guessed inherited mapping or manual refmap JSON replacement is adopted. C7 owns the exact edge cases. [S1, §4/E8; S2, C7]

Do not upgrade the engine or automatically bundle/init MixinExtras, infer Loader predicates or impose new Loader-version restrictions from metadata alone. An operation-scoped task plugin may explicitly initialize an extension, without certification of arbitrary Extras versions. Real incompatible bytecode/configuration and injector/bootstrap failures retain engine failure semantics and cannot become success evidence. Wider support requires concrete consumer evidence and separate accepted coverage. [S1, §5/E10–E11; S2, C8]

## Consequences, compatibility and obligations

The retained architecture makes engine-owned static state disposable at the operation boundary and keeps class/resource identity in declared loading domains. Its costs remain per-operation bootstrap/classloading, resource ownership and version-bound engine adaptation. The short selector window uses the engine's native service/bootstrap selection instead of maintaining synthesized service resources, but requires cooperative initialization exclusion and reliable restoration. Child global-property installation remains private/version-coupled: a child-local Map is not the JVM's string-valued `System` property table, and no native global-property selector bridges that difference. Nonparticipating hosts can observe or interfere with the temporary selector values. Stronger arbitrary-host containment is not promised. Classloader isolation is not a sandbox for plugin-written JVM properties, external threads, native state, filesystem or network effects. No allocation, throughput or memory result was measured in ADR preparation. [S1, §§2–3; S2, C2; S10; current Spec][spec]

For the old compatible/selective scope, keeping entry points avoided a registration change, and a local selective capability avoided spreading the feature through unrelated core listing consumers. Its additional costs were records/binding validation, staged pair publication, complete obligation/failure/residual evidence, Fabric/Forge selective adapters and conservative rejection of unsafe partial/dynamic/plugin results. Digests associated supported Codev-produced records with inputs/outputs; they did not authenticate malicious producers. Those benefits and obligations explain the historical decision, not requirements of the current target. External consumer registrations were not presumed to adopt that path. [S1, §§2–6; S2, C1–C5]

At preparation, the [old Spec acceptance mapping][acceptance], A1–A12, defined the required real-engine/TestKit observations. S10 established only a bounded pinned-engine success/optional-failure distinction and residual mutation, with a source/binary API mismatch and private-access risk; no success adapter was then integrated into Codev, and full C4/A4/A7 or G1 acceptance was not then complete. Later scoped implementation and accepted/closed registration were recorded in the historical results (original deleted), including failed, partial and unknown outcomes. This maintenance neither reruns those checks nor replaces the historical judgments with preparation-era pending statements; old A/AC associations do not validate the new PRD merely because some identifiers match.

For the new target, separate transformed target and dependency copies protect original inputs without policing downstream purposes. Exact dependency configuration-entry cleanup follows engine application notifications, exact logical-key matching and component completion/reuse obligations; it is not legacy all-delete or runtime suppression. Selective residual/runtime-retention restrictions must not become blanket fatal handling of optional engine failures. Application notifications must be distinguished from discovery/candidate callbacks; unnotified identities remain, while partial or unknown application elsewhere does not disqualify notified identities. Engine exceptions, cancellation and Codev cleanup, output-write, selector-restoration or owned-resource exit failures must not expose a current half-result or stale success. Native side/plugin decisions, required/optional behavior and unavailable-plugin/refmap fallback, including a normal default-mapper return, remain the engine's policy: logged errors or partial application with normal return alone do not fail Codev production or disqualify notified identities. Codev does not reclassify them through pre-scans, post-transform audits or log interpretation; necessary mapping and explicitly requested refmap contexts remain required. The [Spec][spec] owns detailed completion, logs/exceptions, input tracking and cache-restored usability without independent records or returned diagnostics. The Spec fixes the Task/Transform structure, named file interfaces, source-independent Strip input, host/child seam, Core-reusing configuration handlers, separate metadata adapters and independent producer lifecycles described above. `GradleMixinRecorderExtension` supplies config and corresponding Mixin for exact mapping back to original logical keys; attribution is no longer an unresolved architecture choice or a new proof gate, but correct implementation still needs verification. The selected Kotlin serialization DOM and library-standard policies for duplicate object keys and unescaped string control characters are defined by the Spec, together with the accepted default UTF-8 decoding and JDK resource-open boundaries above; library edge behavior has not been measured here. Compatibility with strict rejection of malformed UTF-8 or preservation of an opening `IOException` cause is not promised: malformed bytes may be replaced and an open failure may appear only as an unavailable resource. These are bounded compatibility/diagnostic tradeoffs, not permission to ignore conversion or I/O failures generally. Required-input failure, available causes, actual read/close and direct file/JAR failures, selector restoration, exact cleanup and protected inputs retain their obligations, subject to native normally returned fallback. Neither choice proves explicit-context wiring or every real fault exit feasible; the earlier strict-boundary refmap investigation was bounded evidence about the then-examined single-read contact points, not proof that all approaches are impossible. No new single-read refmap protocol or framework is selected here. Remaining API/wiring, completion/storage/restoration and cache details are choices within the accepted interfaces and lifecycles, not grounds to call the whole structure undecided. Real isolation, notification-to-key mapping, dependency/resource/failure protection, concurrent destination ownership and current-input reuse remain implementation and verification obligations. Neither historical Kotlin migration nor old G1 acceptance demonstrates this new structure's implementation or acceptance.

G2–G5, shared cache/lock redesign, remapper reuse, includes identity, launches/native/IDEA work, legacy Loader restoration, versions and publishing remain outside this decision. External consumer rewiring was outside the old delivery; downstream use and routing remain the user's decision, not observed integration or an accepted Codev wiring design. Existing AW/class-tweaker, Fabric AW, Forge AT/patch and nested-JAR capabilities remain baseline concerns on touched paths, not newly certified behavior. The assessment's missing legacy-forge directory/toolchain concern is historical build context; this ADR neither fixes nor reproduces it. [S1, §§6–8; S2, Authority and boundary]

## Revisit criteria

Reconsider or supersede the retained isolation/engine decision if its loading, resource or selected-version assumptions fail. The records/publication/selective-safety triggers below preserve the old scope's revisit conditions only; they are not prerequisites for the current output-use-neutral target. New-target completion, dependency-cleanup and cache-restoration gaps belong in the Spec without silently adopting a new architecture; downstream purposes and routes remain the user's decision.

- For the current target, a concrete supported consumer needs strict malformed-UTF-8 rejection, identical replacement across readers or the original loader-open `IOException` cause, or the selected defaults prevent required input/context semantics or honest failure handling. Reconsider that bounded decoding/open tradeoff against the Spec with concrete evidence; do not silently add strict scanners, cause-recovery pre-reads or a new refmap framework. Default replacement and JDK `null` alone are accepted behavior, not failures of isolation. [Current Spec][spec]
- For the current target, the locked engine no longer supports child-owned service/global-property installation and caching, participating host copies cannot share the short initialization exclusion or restore selectors reliably, or a concrete consuming host requires stronger containment than the observable selector window provides. Reconsider the version-bound adaptation or execution boundary with that evidence; do not claim an arbitrary-host sandbox or serialize whole transformations by default. [Current Spec][spec]
- The bounded pinned-engine reconciliation cannot be validated for a required application/failure path: private access is unavailable, source/binary surfaces differ, native exception attribution is unreliable, later transformation/output commit fails, or complete target obligations cannot be established. Selective-ready production must then fail; another instrumentation/adaptation choice needs review without automatically upgrading the engine. The successful Good/Bad case does not settle these paths. [S10; S2, C3–C4/A4/A7]
- Selective evidence cannot distinguish wholly untouched entries from attempted failures, or a claimed no-residual/runtime-retention proof does not cover all applicable obligations. Reject those selective results, including zero-success failed entries; any broader admissibility needs separately reviewed evidence rather than treating reconciled non-completion as rollback or reapplication safety. [S10; S2, C4–C5/A7]
- Isolation or resource proofs fail: operation A affects B, host/task classes disagree with resources, a competing service replaces Codev's implementation, TCCL/resources survive an exit, or independent operations/output ownership cannot meet C2. Concrete unavoidable plugin global side effects can justify reconsidering process/worker isolation. [S2, C2/A2–A4]
- Publication/binding proofs permit half-results, stale current success or mismatched cached/restored records after failure, cancellation, interruption or retry. A different completion/publication design must preserve C3–C4 rather than weakening evidence checks. [S2, C3–C4/A4–A5/A11]
- Product requirements demand broader partial multi-target, attempted-failure retention, plugin/parent or dynamic re-supply support. That requires an accepted safety/suppression/proof contract and demonstrated consuming scope before replacing that historical selective failure default; the scratch mechanism proof supplies no rollback or runtime-suppression architecture. [S10; S2, C4–C5/A7]
- The engine/ASM lock or Minecraft/Loader/MixinExtras support matrix changes, or a concrete consumer requires Loader predicate alignment or official Extras bootstrap. Recheck success hooks, service discovery, mapping semantics and extension compatibility against the selected versions; no automatic support expansion follows from this ADR. [S1, §5; S2, C7–C8/A9–A10/A12]
